# Mobile UI, 18/10/2026

Design read: evolve the existing HANU profile manager for phone use. Preserve its green accent, Geist type, Fluent components, routes, form labels and execution behavior. Variance 3, motion 2, density 5. Taste's landing-page imagery and marketing layouts do not apply to this operational UI.

## Audit

- The 390 px header wraps and clips account actions. The profile table remains 890 px wide and requires horizontal scrolling.
- Small text and compact desktop buttons make status and actions hard to use by touch.
- Long profile details compete with a footer containing every control, leaving little editing space.
- Existing light/dark tokens and explicit states are worth preserving. No route, auth policy, file-transfer protocol, profile schema or autofill engine change is needed.

## Implementation

- Existing table rows become touch-friendly cards below the sidebar breakpoint; tablet widths support two columns. A single set of checkbox and action handlers serves both layouts.
- The original Start button moves into a mobile dock with the selected count and mode. No duplicate Start control or new execution path is added.
- Account utilities use an official Fluent dialog. Profile secondary controls use a Fluent popover, keeping Save visible. The custom detail overlay defers keyboard handling to nested Fluent surfaces and restores body scrolling on close.
- Mobile uses 44 px targets, 16 px inputs, safe-area padding, wrapped account/status text, and contained form scrolling. Existing desktop tables and account/admin routes are retained.

## Verification

- Typecheck and both cloud/native manager builds pass.
- `npm run test:mobile-ui`: passes at 320, 360, 390, 430, 768, 900, 1024 and 1440 px. Covers bounded page width, tablet cards, a visible single Start control, selection through filtering, group pause/resume/stop, per-profile Restart, Save, secondary popover focus/Escape, cancel unlink, file chooser, login/account/admin and light/dark mode. No page errors. The fixture uses synthetic accounts and mocked extension commands; no real Google form is submitted.
- Existing cloud and local-manager UI regressions pass. The local-manager check had a stale assertion waiting for `/api/start` after a per-profile Restart; corrected it to wait for the existing `/api/sessions/:id/restart` endpoint. The application request path is unchanged.
- A test caught a Fluent modal remaining open during SPA logout and leaving the next page hidden from accessibility APIs. The tools dialog now uses the existing inert/no-motion pattern and its logout action closes through `DialogTrigger` before logout resolves. The keyboard/login regression passes.
- Screenshots and browser audit are under `test-results/mobile-20261018`. Lighthouse with provided/local conditions: performance 100, accessibility 96, best practices 100; LCP 0.2 s, TBT 0 ms, CLS 0. This is a local, unthrottled measurement, not a phone/network guarantee. Its remaining accessibility warning is for Fluent/Tabster's two 1 px focus sentinels (`body > i[data-tabster-dummy]`); focus guards were not disabled or hidden to improve a score. The initial simulated mobile audit scored 68 performance with uncompressed local assets and an auth-fixture redirect; that report is retained separately.
- Applicable taste pre-flight: existing brand/type/system and route/field labels preserved; restrained feedback, clear focus, native Fluent surfaces, contrast correction, safe-area and dynamic-height layout, readable inputs, no page-wide horizontal overflow and explicit empty/error/selection states. Marketing hero, photography and landing-page composition rules do not apply to this management app.
- Production deploy evidence and post-deploy responsive checks are recorded separately in `test-results/mobile-20261018/post-deploy.json` and the final report. This change does not modify the extension, upload, approval, submit-lock or registration engine.
